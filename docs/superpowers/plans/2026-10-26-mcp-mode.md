# MCP Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the app as an npm CLI `browser-fix` that runs today's interactive repair flow by default (standalone), or a stdio MCP server when started with `--mcp`, so Claude Code can drive the browser and read captured errors.

**Architecture:** A new CLI entry (`src/cli.ts`) parses `--mcp` and `--url <url>`, loads shared `.env` config and dispatches to `runStandalone` (today's `src/index.ts` behaviour, unchanged) or `runMcp`. MCP mode reuses `BrowserConsoleListener` and `ErrorDeduplicator`, buffers deduplicated errors in an `ErrorStore`, and exposes three tools (`open_browser`, `get_errors`, `close_browser`). When `--url` is given, the browser opens on that URL as soon as Claude Code starts the server. Claude Code, not the built-in repair agent, does the fixing.

**Tech Stack:** TypeScript (ESM, nodenext), Playwright, `@modelcontextprotocol/sdk` (stdio transport, `McpServer.registerTool`, zod v4 schemas), `node:test` run through `tsx`.

**Spec:** No spec document. The source is the user's request in conversation: "standalone mode is that when user run `npx browser-fix`, it will open an playwright browser like it is currently doing, while in the mcp mode, it can be installed to claude code like `{ "mcpServers": { "browser-debugger": { "command": "npx", "args": ["-y", "browser-fix", "--mcp"] } } }`". The user also confirmed that no `.env` key is needed: the mode comes only from the CLI flag. In a follow-up they added: "if it is in the mcp mode, claude code can run this app to listen to the url as cmd parameter".

**Assumptions (confirm in review):**
- The URL is passed as `--url <url>`, e.g. `"args": ["-y", "browser-fix", "--mcp", "--url", "http://localhost:5173"]`. It overrides `TARGET_URL` in both modes.
- The URL can be changed at any time from Claude Code. The user says something like "use browser fixer for url http://emsdev.localhost:8080" and Claude calls `open_browser { url }`, which opens the browser or switches the open one to that URL. `--url` is only the starting URL.
- In MCP mode **with** `--url`, the browser opens on that URL when the server starts and listens straight away. **Without** `--url`, the server waits for the `open_browser` tool, which falls back to `TARGET_URL`, so a config with no URL doesn't pop up a browser in every Claude Code session.
- MCP mode has no console prompts and does not run the built-in repair agent. stdin/stdout carry the MCP protocol, and Claude Code's own permission prompts gate any edits. `WORK_DIRECTORY` and `ANTHROPIC_API_KEY` are therefore not required in MCP mode.
- Publishing to npm is **out of scope**. `npx -y browser-fix` only works once someone publishes the package. The name `browser-fix` was unclaimed on npm on 2026-10-26. Publishing is outward-facing and needs the repo owner's decision. Before that, test locally with `"command": "node", "args": ["<repo>/dist/cli.js", "--mcp"]`.

## Global Constraints

- Package name `browser-fix`; bin `browser-fix` → `dist/cli.js`; CLI grammar `browser-fix [--mcp] [--url <url>]` (any order); no `--mcp` = standalone; any other argument, a missing value or an invalid URL → `Usage: browser-fix [--mcp] [--url <url>]` on stderr, exit 1.
- In MCP mode **nothing may be written to stdout except MCP protocol messages**. Load dotenv with `{ quiet: true }`.
- **No Claude tokens for capture.** Listening to the URL, filtering, de-duplicating errors and warnings (per `CONSOLE_TYPES`) and buffering them all run locally, with no Anthropic API calls. In MCP mode the server never pushes anything to the client unprompted: no notifications, logging messages or sampling requests. Tokens are spent only when Claude calls a tool and reads its result. In standalone mode, tokens are spent only after the user approves a fix at the first `y`/`n` prompt, as today.
- Standalone behaviour, including the three console gates in CLAUDE.md (`y`/`n` → `fe`/`data` → `y`/`n`), must not change.
- ESM imports need `.js` extensions; use `import type` for type-only imports; `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are on.
- Code comments and log messages are in English. Docs use Australian English.
- Add `@modelcontextprotocol/sdk` as a direct dependency (it is only a transitive dependency today; 1.31.0 is installed and its peer range accepts zod ^4).

## Review Focus

1. **Stray stdout in MCP mode** (dotenv banner, `console.log` in the listener or in `debug()` with `log.level=debug`) corrupts the protocol and Claude Code shows the server as failed. Expect the handshake to succeed with `log.level=debug` → Task 4 integration test.
2. **User closes the browser window in MCP mode.** Today the listener calls `process.exit(0)`. In MCP mode the server must stay up and `open_browser` must relaunch → Task 3 `BrowserSession` test.
3. **Browser fails to launch** (e.g. a second Claude Code session's server holds the `USER_DATA_DIR` profile lock, or Chrome is not installed). Expect a tool error naming the cause, with the server still running → Task 3 server test.
4. **Startup open with `--url` fails** (dev server not running yet, profile locked). Expect the server to stay up and log the failure to stderr, with `get_errors` reporting "not open" and `open_browser` able to retry → Task 3 `openOnStartup` test.
5. **Error flood between `get_errors` calls** (e.g. an error inside a render loop). Expect the buffer capped at 100, oldest dropped, and the drop count reported → Task 3 `ErrorStore` test.

### Task 3: Error store, browser session and MCP tools

**Files:**
- Create: `src/mcp/errorStore.ts`, `src/mcp/browserSession.ts`, `src/mcp/server.ts`, and a `*.test.ts` beside each
- Modify: `package.json` (`npm install @modelcontextprotocol/sdk`)

**Interfaces:**
- Consumes: `describeError`, `BrowserConsoleListener` (`start`/`goto`/`stop`, `onClose`) (Task 2)
- Produces:
  - `class ErrorStore { constructor(capacity = 100); add(p: FrontendErrorPayload): void; drain(): { errors: FrontendErrorPayload[]; dropped: number } }`. When full, `add` drops the oldest entry; `drain` empties the store and resets `dropped`
  - `interface BrowserControl { start(): Promise<void>; goto(url: string): Promise<void>; stop(): Promise<void> }`
  - `class BrowserSession { constructor(createBrowser: (url: string, onClose: () => void) => BrowserControl); isOpen(): boolean; open(url: string): Promise<'opened' | 'navigated'>; close(): Promise<boolean> }`. `open` creates and starts a browser when none is open, otherwise calls `goto`. A failed `start` leaves the session closed and rethrows. `onClose` marks the session closed. `close` returns `false` when nothing was open
  - `createMcpServer(session: BrowserSession, store: ErrorStore, defaultUrl: string): McpServer`, named `browser-fix`, with the version read from `package.json`. Tools:
    - `open_browser`, input `{ url?: string }` (zod `z.string().url().optional()`). Opens the browser on `url ?? defaultUrl`, or switches the already-open browser to it, and listens for errors there. It returns `Browser opened, listening on <url>` or `Switched to <url>, listening for errors there`. When it switches, it first clears the store so `get_errors` doesn't mix in errors from the previous URL. The description must make Claude call it whenever the user names a URL to debug, fix or listen to. Write it as: `Open the browser (or switch the open browser) to a URL and listen for frontend errors there. Call this when the user asks to use the browser fixer/debugger on a URL, e.g. "use browser fixer for url http://emsdev.localhost:8080". Without url, uses TARGET_URL or the --url startup argument.`
    - `get_errors`, no input. Drains the store. With no errors it returns `Browser is not open. Call open_browser first.` when the session is closed, else `No new frontend errors captured since the last call.` Otherwise it returns `<n> new error(s):` followed by each `describeError(...)` joined with `\n\n---\n\n`, plus `(<k> older errors dropped)` when `dropped > 0`
    - `close_browser`, no input. Returns `Browser closed` or `Browser is not open`
    - Server `instructions` and the `get_errors` description must say that `Location` is 1-based while stack-trace lines are 0-based, and that the error should be fixed in the user's project, not in `node_modules`
  - `openOnStartup(session: BrowserSession, url: string): Promise<void>` in `src/mcp/server.ts`: calls `session.open(url)` and never rejects; on failure it logs `❌ Could not open <url>: <message>` via `console.error`
    - Any thrown error in a handler → `{ isError: true, content: [{ type: 'text', text: 'Failed to <action>: <message>' }] }`. The `open_browser` failure text also names `USER_DATA_DIR` as a possible lock cause
